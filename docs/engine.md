# 引擎：现有什么

引擎目前是一副**骨架**：读语料、检索、度量自己。先做它，是因为延迟和常驻内存这类问题只能在真实硬件上量出来，不能在纸面上定。

## 现有

```
engine/
  crates/folio/        打开 .folio：清单校验 · 单元 · f16 向量 · 名册 · 别名 · 提示词 · 措辞
  crates/index/        混合检索：别名展开 → 词法 BM25 ∥ 精确稠密扫描 → RRF 融合 → 置信度 → 邻居扩展
  crates/eval/         结构评测集的运行器与指标，按族、按层报告
  bins/dramatis-cli/   inspect · search · evaluate · bench
```

语料路径来自 `--folio` 或环境变量 `DRAMATIS_FOLIO`，评测集来自 `--suite` 或 `DRAMATIS_SUITE`。没有缺省路径：写死的路径就得点名产出语料的配置包。

**folio**：一个 SQLite 文件装下运行时需要的一切。向量是按 `chunks.ord` 排列的一整块 f16，打开后按需载入。

**index**：
- *别名展开*。查询里的名字先查别名词典：只有别名、正文里从不出现的实体，只能靠这张表找到。三种设置（关闭 / 只展开 / 展开并在唯一指向一个人时限定到这个人）就是评测要比较的三个系统。一个名字指向多个对象时，返回的是一个可报告的「歧义」状态和全部候选，而不是替用户挑一个。
- *词法路*。FTS5 + BM25，查询端的分词必须和建库时一致，所以分词器身份从清单读取。查询端停用词同样来自清单的 `stopwords` 键，由配置包提供：哪些词没有检索信号是语料语言的属性。停用词只从查询里去掉，索引里保留。
- *稠密路*。对全部向量做精确扫描，没有近似索引：少一个依赖、少一步构建，维度消融曲线里也没有近似误差。
- *融合与置信度*。RRF 融合两路结果；置信度由三个信号共同给出：最高分、两路候选的重合度、分数分布的熵。第三个信号用来识别「每个候选都半相关」的情况，这时正确的做法是承认档案里没有明确答案。
- *邻居扩展*。单元只存一次、互不重叠；需要上下文时，按 `span_of` / `span_from` 把排好序的命中向两边扩展。

**eval**：读取 forge 生成的 JSONL 评测集，逐条打分，比较两套配置时用配对 bootstrap。不给单一总分：各族大小悬殊、考的东西不同，逐字层又能被精确匹配直接解决，所有东西的平均值没有所指。唯一提供的汇总是宏平均，它只是摘要，不是结论。

**dramatis-cli**：
- `inspect`：语料里有什么，对读者提出了什么要求。
- `search`：跑一遍管线，显示结果和每个阶段的耗时。
- `evaluate`：对照结构评测集打分，按族、按层；可以同时跑三种别名设置并两两比较。
- `bench`：每个阶段的延迟分布和常驻内存。查询从语料本身抽取（每个模板至少一条），而不是写死在代码里的词表。常驻内存从操作系统读，不估算。

## 没有

智能体循环、世界状态、审批闸门、客户端。没有空的 crate 目录顶替它们：一棵空 crate 树看起来像进展，其实不是。

## 两条由代码强制、而不是靠纪律的契约

- 不认识的 `format_version` 直接拒绝加载。格式版本变了意味着某一列的含义变了，猜测新含义正是读者开始答错的方式。
- 清单 `requires` 里声明、而本构建没实现的能力，直接拒绝加载。忽略 `neighbor_expand` 会返回看上去完整、其实被截断的答案。

## 度量本身也要被验证

有些失败读代码看不出来，只有跑起来才看得见：一个高频词让 BM25 几乎给全库打分；SQL 按候选数重新拼接，于是永远不进缓存；先截断再过滤，于是什么也不返回。度量本身也可能错：在当前 macOS 内核上，旧的 `TASK_BASIC_INFO_64` 返回成功，报告的常驻内存却是零。**系统调用成功不等于度量正确**，所以 `bench` 用的读法是对着一个刚触碰过已知内存量的进程核对过的，并同时报告当前值与 `getrusage` 峰值。

当前数值不在这里。对一份构建好的语料运行 `dramatis-forge report figures` 与 `dramatis-cli bench`。
